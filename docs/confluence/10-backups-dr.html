What is backed up, where every copy lives, how to restore on the same hosting or move to a new provider, and how to prove afterwards that every credential works. Every step was tested in a restore drill on 16 Nov 2026.

Two files are never in the backup folder and cannot be recreated: app/config.php and app/keys/app.key. Keep both in the password manager (two copies). Without app.key, encrypted data (contacts, customer database passwords, stored secrets) can never be read again.

2. The nightly backup job

  1. hPanel → Advanced → Cron Jobs. The job must exist, daily at 2:00:
    /usr/bin/php /home/USER/domains/clockinoutapp.com/public_html/cron/backup.php
    (USER = your hosting user, shown at the top of hPanel → File Manager; never write it in public places).
  2. Run it once by hand to test: on the Cron Jobs page click Run/"View output", or over SSH run the same command. A good run prints one line per database and Saved to …/backups/2026-11-16_0200.
  3. Check the folder: File Manager → public_html/backups/ → newest folder → open MANIFEST.txt. It lists every database with its row count, the logo archive, and the restore commands.
  4. The job tests that every .sql.gz opens and writes a SHA-256 checksum per file. A failed database prints FAILED and the job ends with an error (shown in the cron output and as a red "Nightly backup" on /status).
ClockInOut backup 2026-11-16 21:44 UTC

clockinout (main)                            2572 rows
uploads_logos.zip                               3 files

Restore one database:  gunzip -c FILE.sql.gz | mysql -h HOST -u USER -p DATABASE   (or phpMyAdmin → Import)
Check a downloaded copy: sha256sum -c SHA256SUMS   (Windows: certutil -hashfile FILE SHA256)
Not in this folder (keep them in the password manager): app/config.php and app/keys/app.key

3. Weekly off-site copy (5 minutes, every Monday)

  1. hPanel → File Manager → public_html/backups/ → right-click the newest folder → Compress → zip → download it.
  2. Save it to OneDrive or Google Drive in a folder "ClockInOut backups". Keep 4–8 weeks.
  3. Check the download is not damaged: unzip it, then 
    # Mac / Linux, inside the folder
shasum -a 256 -c SHA256SUMS
# Windows PowerShell, one file at a time; compare with the line in SHA256SUMS
Get-FileHash .\main_clockinout.sql.gz -Algorithm SHA256
    Every file must say OK / match.

4. Recovery objectives

Data loss at most 1 day (nightly backup). Restore on the same hosting: 15–30 minutes. Move to a new provider: 1–3 hours, plus DNS time.

5. Restore: the two paths

6. Path A — restore on the same Hostinger account

A1. One customer's data is wrong or lost (customer with its own database)

  1. File Manager → backups/ → the newest folder from before the problem → MANIFEST.txt → find the line with the portal name; the file is <slug>_<database>.sql.gz.
  2. hPanel → Databases → phpMyAdmin → open that customer's database → Import → choose the .sql.gz → Go. The file replaces the tables with the backed-up version.
  3. Or over SSH: 
    cd ~/domains/clockinoutapp.com/public_html/backups/2026-11-16_0200
gunzip -c acme_u_acme.sql.gz | mysql -u DB_USER -p DB_NAME   # asks for the database password
  4. Run the restore check (section 8).

A2. Customer in the shared database

  1. phpMyAdmin → create an empty scratch database (e.g. restore_tmp) → Import the main_….sql.gz into it.
  2. Copy only that customer's rows back (every table has tenant_id). Ask Claude to write the exact SQL for the tables you need; never import the main file over the live database for one customer.
  3. Delete restore_tmp afterwards.

A3. The whole platform database is damaged

  1. Put the site in a safe state: rename public/index.php to index.off.php and upload a one-line index.php that says "Back soon" (optional).
  2. phpMyAdmin → platform database → Import main_….sql.gz (or gunzip -c main_….sql.gz | mysql -u DB_USER -p DB_NAME).
  3. Put index.php back. Open the site once (the database upgrades itself if the backup is older than the code).
  4. Run the restore check.

A4. The code is broken (after an update or a hack)

  1. Download the last good release zip (your previous upload, or GitHub → aspireitech/Timeinout → Code → Download ZIP of main).
  2. File Manager → public_html → Upload → Extract → overwrite. app/config.php, app/keys/, backups/ and public/uploads/ are not in the zip, so they are kept.
  3. After a hack: also change every password and key in the credentials register (section 9), then run the restore check.

A5. Logos missing

Unzip uploads_logos.zip from the backup folder into public_html/public/uploads/logos/.

A6. The whole account is broken

hPanel → Files → Backups → restore the newest Hostinger snapshot; then A1–A3 for anything newer than the snapshot; then the restore check.

7. Path B — move to a new hosting provider (or a new Hostinger account)

Do steps 1–6 while the old site still runs. Customers notice nothing until step 8, and only for minutes.

  1. Collect (old host or your off-site copies):
    • the newest backup folder (section 3; take a fresh one on the old host if it still works: run cron/backup.php by hand)
    • app/config.php and app/keys/app.key from the password manager
    • the code: GitHub main → Download ZIP
  2. New server requirements: PHP 8.1 or newer with pdo_mysql, openssl, curl, mbstring, zlib, zip; MySQL or MariaDB; cron jobs; free SSL (Let's Encrypt); SSH access is helpful.
  3. Upload the code into the web folder (the folder the domain points to), so that .htaccess and the public/ folder are directly inside it. Then put back the secrets: 
    cd ~/path/to/webfolder
mkdir -p app/keys backups app/sessions public/uploads/logos
# upload config.php to app/ and app.key to app/keys/ (File Manager or scp), then:
chmod 600 app/config.php app/keys/app.key
chmod 755 backups app/sessions public/uploads/logos
  4. Databases: in the new panel create the platform database and one database per customer that had its own (names in MANIFEST.txt). Same names and passwords as before are easiest. Then import: 
    cd ~/restore/2026-11-16_0200
gunzip -c main_clockinout.sql.gz | mysql -u NEW_DB_USER -p NEW_DB_NAME
# one line per customer database listed in MANIFEST.txt:
gunzip -c acme_u_acme.sql.gz | mysql -u ACME_DB_USER -p ACME_DB_NAME
sha256sum -c SHA256SUMS     # before importing: every file OK
    No SSH? Use the new panel's phpMyAdmin → Import, one file at a time.
  5. Update the logins that changed:
    • platform database: app/config.php → 'db' → host, name, user, pass
    • a customer database: /super → Subscribers → that portal → database details (saved encrypted)
  6. Logos: unzip uploads_logos.zip into public/uploads/logos/.
  7. Cron jobs with the new paths (find the PHP path with which php or the panel's help): 
    hourly   /usr/bin/php /home/NEWUSER/…/webfolder/cron/send_reports.php
daily 2:00  /usr/bin/php /home/NEWUSER/…/webfolder/cron/backup.php
  8. Run the restore check now (section 8). Everything except "reaches this server" must be OK before DNS is switched.
  9. Switch DNS: a day before, lower the TTL to 5 minutes in Namecheap. Then Namecheap → Domain List → clockinoutapp.com → Advanced DNS → A records @, www and * (wildcard for customer subdomains) → the new server's IP. Do not change the MX, SPF, DKIM and DMARC records: email stays at Microsoft 365.
  10. SSL on the new server for clockinoutapp.com, www and the wildcard (or one certificate per customer subdomain).
  11. Run the restore check again until "https://clockinoutapp.com reaches this server" and the subdomain lines are OK (DNS can take minutes to hours).
  12. Keep the old host for one week, then cancel it.

8. After any restore: prove every credential works

The restore check tests each credential for real and says where to fix what fails. It never shows a secret.

  • Browser: /super → Restore check (top menu) (page /super/check). Optionally type your email to also receive a real test email.
  • Server: 
    php ~/domains/clockinoutapp.com/public_html/cron/verify_restore.php --send-test=you@example.com
    It first upgrades a restored database to the current code, then prints OK / WARN / FAIL with a "fix:" line, and ends with exit code 0 (all good) or 1 (something failed).

The example above is a test machine: it correctly reports that the hourly job is not running there and that clockinoutapp.com still reaches the live server, which is exactly what you see on a new server before DNS is switched.

9. If you suspect a break-in

  1. Restore the code (A4) and the database from before the break-in (A1–A3).
  2. Change, in this order: hosting panel password, database passwords (panel → then config.php / portal settings), Microsoft client secret (Entra → new secret, delete the old one), Stripe secret key (roll it) and webhook secret, Wave token, Google OAuth secret, prospect finder key, /super break-glass password and recovery codes.
  3. Do not replace app.key (old data would become unreadable) unless the key itself leaked; then ask Claude for a re-encryption plan first.
  4. Run the restore check; read /super → Audit log for what happened.

10. Every upload is security-checked first

Every update zip is built only after the release check passes: PHP syntax, no secrets or local files in the code, security headers, protected folders, form protection (CSRF) and verified webhooks, no request data in database queries or redirects, no new unescaped output in pages, and database changes that only add. If any check fails, no zip is built.

php cron/release_check.php --zip ClockInOut-update.zip

11. Practice once a quarter (restore drill, 20 minutes)

  1. phpMyAdmin → create an empty database drill_YYYYMM.
  2. Import the newest main_….sql.gz into it; the import must finish without errors.
  3. Check the row counts against MANIFEST.txt (phpMyAdmin shows rows per table).
  4. Verify your off-site copy with SHA256SUMS (section 3) and that config.php and app.key in the password manager match the server (compare the first lines).
  5. Run the restore check on the live site; then delete the drill database.
